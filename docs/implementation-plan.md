# フロントエンド実装計画

作成日: 2026/10/17

## 目的と今回の成果物

`docs/spec.md` のアプリ仕様と `docs/design/医療業務支援タブレットアプリ.html` のClaude Designを基に、Vue 3 + Vuetify 4のフロントエンドを実装するための計画を定める。本ドキュメント作成の段階ではアプリのコードを変更しない。

実装時の到達点は、バックエンドを起動せず、職員カード読み取りのシミュレーション、PIN入力、職種別の業務画面、端末設定、業務画面設定を一連の操作として確認できるアプリとする。14種類の業務コンポーネントを個別に完成させ、同じコンポーネントを業務画面と設定プレビューで描画する。

実際のカードリーダー接続、認証、API、DB、病院内での設定共有、診療データの読み書き、サーバーでの排他制御は今回の対象外。表示データは架空の固定データとし、与薬・点検の操作はデモ内の状態変更として扱う。

## 調査した構成と参照方針

- 既存の `apps/frontend` はVue 3、Vuetify 4、vue-router、Pinia、TanStack Queryを導入済み。`HomeView.vue`、`SampleView.vue` とサンプルAPI呼び出しがあるスターター構成。
- ルート定義は `src/router/routes.ts`、履歴生成は `src/router/index.ts` に分かれている。この構成を維持する。
- デザインHTMLは単純な静的画面ではなく、バンドル内の `window.__MS_SOURCES` に `vue-app/src/` のSFC、病棟・職員マスタ、患者データ、配置処理を含む。これらを読み取り、表示内容・サイズ・初期配置の参照にする。
- デザインの実行用ローダー、ベンダーバンドル、画面一覧用のラッパーは移植しない。既存Vite構成でSFCをビルドする。
- 仕様書を要件の基準とし、見た目と具体的なデモ操作はデザインを参照する。デザイン独自の振る舞いは以下の「暫定方針」で区別する。
- `AGENTS.md` と `apps/frontend/AGENTS.md` に従い、Composition API、`<script setup lang="ts">`、アロー関数を使う。デザイン内の一体化したストアや関数宣言をそのまま転用しない。

## 実装前に揃える暫定方針

以下は仕様を補う実装案であり、既存の確定要件とは区別する。実装に着手する段階で `docs/spec.md` に反映する。PINなどの制限値は仕様のリミット値表とコードを同時に更新し、本文への重複定義を避ける。

| 論点                       | 今回の方針                                                                                       | 根拠・扱い                                                                         |
| -------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| PIN待機時間                | 無操作30秒でカード待ちへ戻る。数字入力・削除で期限を更新する                                     | デザインの暫定値。仕様のリミット値表に登録する                                     |
| PIN入力                    | 4〜6桁の数字、明示的な確定操作。デモ用の正解PINは1234                                            | 桁数は仕様、デモ用PINはデザイン。認証の代用であることを表示する                    |
| 端末病棟と職員             | 職員選択で端末病棟を変更しない。ユーザーIDと職種IDを分離する                                     | デザインのシーン初期化は職員と病棟を同時に変更するが、通常操作は端末設定を優先する |
| レイアウトの優先順位       | 職種＋端末病棟 → 職種の全病棟共通 → 病院全体                                                     | デザインの実装を採用する                                                           |
| レイアウト件数             | 病院全体は固定1件、職種と病棟の組み合わせごとに1件。重複追加を不可とする                         | デザインでは登録済みの追加ボタンが無効。仕様に追記する暫定制約                     |
| 追加時の初期内容           | 現在有効な画面を複製して下書きを作る。決定まで保存せず、取消で追加自体を破棄する                 | デザインは追加直後に登録するため、取消の意味を明確にする改善案                     |
| 重なる配置                 | 配置範囲と置き換え対象を明示し、タップで重なるコンポーネント全体を下書きから除く                 | デザイン準拠。決定するまでは保存済み配置に影響しない                               |
| 同じコンポーネントの再配置 | 同一画面内は同種1個。配置済みの種類を選んで置くと移動する                                        | デザイン準拠。別画面にはそれぞれ配置できる                                         |
| 端からの配置               | 定義サイズが収まる最寄りの起点へ補正し、補正後の範囲を表示する                                   | デザイン準拠。負の座標・不正な値は拒否する                                         |
| 未保存での離脱             | 戻る・画面切替・ログアウト時に差分があれば破棄確認。キャンセルボタンは明示的な破棄               | 誤操作防止の暫定方針                                                               |
| 病棟未設定・不正設定       | 病棟未設定を明示し、デフォルト画面にフォールバック。設定導線を提示する                           | デザインの暗黙の先頭病棟選択を避ける。初回デモだけ初期病棟を投入する               |
| 患者の選択                 | 各病棟に架空患者1名を割り当て、全ウィジェットで同じ患者を参照する                                | 患者選択機能は仕様にないため追加しない                                             |
| 医療計算・記録             | デザイン内のスコア・換算値・注意文はサンプル値として表示する。与薬・点検はメモリ上のデモ操作のみ | 計算エンジンや診療記録機能の要件を新設しない                                       |
| PWA                        | manifestとアイコン、対応ブラウザでのインストールを用意する。オフライン用キャッシュは実装しない   | 仕様のPWA提供とオフライン非対応を両立する                                          |

## フロントエンドの構成

### コンポーネント登録と描画

`src/features/workspace/` にレイアウト型、コンポーネントのレジストリ、配置処理を置く。レジストリは各種類について `id`、名称、短縮名称、概要、固定の幅・高さ、SFCの参照を持つ。Vueの `<component :is>` で描画し、ユーザー入力からファイルパスやSFC名を生成しない。

配置データは `{ componentId, column, row }` の配列とし、座標は0始まり。幅・高さはレジストリから導出し、保存データに重複させない。レイアウトは `id`、`roleId`、`wardId`、`items` を持ち、病院全体は両スコープをnull、職種共通は `wardId` をnullとする。

`LayoutGrid` は描画と空き領域の表示、`WidgetHost` は登録済みSFCの解決、`WidgetCard` はタイトル・補助表示・本文・スクロールの共通枠を担う。業務画面と編集プレビューは同じ描画経路を使う。編集プレビューには操作不可のモードを渡し、与薬や点検などの副作用を起こさない。

### データと状態の分担

| 種類                                 | 保存先・実装                                            | 方針                                                                                                |
| ------------------------------------ | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 病棟、架空職員、患者の初期データ     | `src/demo/` の型付きfixture                             | 患者IDで一貫したデータを参照し、職種切替で別患者が混入しない                                        |
| 患者の表示状態・デモ記録             | TanStack Query用composable + 非同期のメモリ内データ関数 | 成功・待機・空・エラーを切替可能。デモ更新後は関連キーをinvalidateする。Piniaに患者データを置かない |
| デモのログイン情報                   | setup形式のPinia store                                  | メモリのみ。PINは確定・失敗・取消・タイムアウトで消去する                                           |
| 端末病棟、保存済みレイアウト         | UI設定用Pinia store + 小さなlocalStorage入出力関数      | schemaVersion付きで保存。病院の共有設定をブラウザ内で模擬する                                       |
| 編集下書き、選択中の部品、配置ガイド | エディターのcomposable/ref                              | 保存済みデータを複製して編集。取消で破棄する                                                        |
| 時計、通知                           | composable / 既存notification store                     | 時計はJSTで表示し、購読解除時にタイマーを解放する                                                   |

localStorageに保存するのは端末設定とレイアウトだけとし、患者情報・PIN・ログイン状態・与薬や点検記録は保存しない。復元時はバージョン、職種・病棟ID、コンポーネントID、整数座標、範囲、重複、衝突を検証する。不正データは採用せず初期設定へ戻す。保存失敗時は通知して下書きを残し、保存成功とは表示しない。

将来APIに接続するときはデータ取得関数をHono RPCに置き換え、API型はbackendの `AppType` から推論する。今回の表示用モデルを共有DTOパッケージにしない。新しい汎用repository層やバックエンドの仮ルートは作らない。

### ルート案

| パス                          | 内容                                   |
| ----------------------------- | -------------------------------------- |
| `/login`                      | カード待ち・PIN・エラー                |
| `/work`                       | 有効なレイアウトによる業務画面         |
| `/settings/terminal`          | 端末病棟設定                           |
| `/settings/screens`           | 業務画面選択・追加                     |
| `/settings/screens/:screenId` | 編集または参照                         |
| `/dev/components`             | 開発時のみの個別コンポーネント確認画面 |

`/` はデモのログイン状態に応じて遷移する。未ログインでの設定直アクセスはログインへ、存在しない画面IDは一覧へ戻す。他職種の画面は編集できず、病院全体の変更は禁止する。これはデモのUI制御であり、サーバー認可の実装ではない。

### レイアウトと外観

- 基準サイズはデザインの横1280×縦800。業務領域740px、システム領域60px、グリッドの余白・間隔8pxを再現する。
- CSS Gridの横4列・縦2行を使い、`minmax(0, 1fr)`、子要素の `min-width: 0` / `min-height: 0`、必要な本文スクロールで溢れを防ぐ。
- 通常画面は利用可能な高さに追従し、システム領域の高さを維持する。小さい画面では可読性を保つ最小幅とスクロールを使い、論理グリッドを勝手に組み替えない。
- 編集画面のプレビューは原寸と表示領域の比率から縮小率を求める。デザインの固定 `scale(0.68)` を端末共通値にしない。タップ用の8セルと表示の座標系を一致させる。
- 主色 `#0E6E66`、濃色 `#0F3B37`、背景 `#E8ECEA`、文字 `#16201E` を既存Vuetifyテーマへ反映する。赤・黄・青などの状態表示は文字やアイコンも併記する。
- 日本語書体、16pxを基準にした本文、数値の桁揃えを確認する。既存のフォント設定を確認してから必要な差分を加える。
- タッチ・クリック・キーボードで操作できるVuetifyのボタン類を使う。ホバーだけで配置範囲を知らせず、選択後やフォーカス時にもガイドを表示する。

### 各コンポーネントの共通完了条件

1. 対応する埋め込みSFCとfixtureを確認し、今回扱う項目を特定する。
2. 型付きpropsと共通カード枠で実装し、部品自身が病棟から患者を独自選択しないようにする。
3. 開発用確認画面で、定義サイズの原寸と縮小プレビューを確認する。
4. 通常・空・欠損・長い内容・エラーを確認し、待機表示はデータ取得を担当する共通部分で確認する。
5. 本体とプレビューで同じ値が見え、プレビューからデモ更新が起きないことを確認する。
6. 表示ロジックに独立した分岐がある場合だけDOM不要の単体テストを追加し、型チェックを通す。
7. 対応する業務画面へ配置し、確認結果と残課題を記録して完了チェックを付ける。

## 検証方法

既存のテスト実行環境はNodeのみ。SFCをマウントするためのjsdom等は導入せず、判定ロジック・store・ルート・queryを直接検証する。テストは対象ファイルと同じ場所に置く。DOMによる表示と操作はブラウザで確認する。

| 対象       | 主な検証                                                                                                    |
| ---------- | ----------------------------------------------------------------------------------------------------------- |
| 配置処理   | 各定義サイズ、2×2の合成ケース、右下の補正、不正座標、衝突した全コンポーネントの除去、同じ種類の移動         |
| 設定の選択 | 職種＋病棟・職種共通・デフォルトの優先順位、別職種への非適用、病棟未設定                                    |
| 編集       | 並び順だけではdirtyにならない、病棟情報を含む設定差分、保存と取消、追加取消、参照のみの更新拒否             |
| 永続化     | 不正JSON、未対応バージョン、未知ID、範囲外・重複・衝突、ストレージ書き込み失敗                              |
| ログイン   | 桁数、数字以外、正誤、期限更新、期限切れ、ログアウト。時計はfake timerで検証                                |
| データ取得 | 患者IDを含むquery key、待機・成功・エラー、デモ更新後のinvalidate、別患者への状態漏れ防止                   |
| ルート     | `routes` と `createMemoryHistory()`、`router.resolve()` で対応を確認。ガードの分岐はDOM不要の処理として検証 |

実装時のチェックは `vp check`、`vp test`、`vp run frontend#build` を実行する。必要に応じてfrontendのテストだけを `vp run frontend#test` で確認する。バックエンドは起動しない。設定やツールの不調時は `vp env doctor` の結果を記録する。
